# Eagle Eye Africa — Consolidated Upgrade Task List

**Purpose:** A single, sequenced implementation plan combining `AUDIT 1.md` and `AUDIT 2.md`. Use this as the working checklist; keep the source audits as evidence, not as competing roadmaps.

**Product outcome:** Make it easy and safe for a community member—especially a first-time user on a low-end phone or unreliable connection—to read and share local stories, find or report lost items, see trusted notices, trade locally, and discover places.

**Planning assumptions:** Preserve the existing Next.js/Supabase architecture, locale-first URLs, English/French parity, guest submission where safe, moderation, corrections, and defense-in-depth security. Treat feature deletions as proposals that require evidence, backup, staged rollout, and explicit data-retention decisions. Do not use a destructive SQL `DROP ... CASCADE` as a substitute for dependency analysis.

## How to use this plan

- Work phases in order. Tasks within a phase may run in parallel only after their listed prerequisites are met.
- Mark a checkbox complete only when its acceptance criteria pass; record owner, date, evidence, and any follow-up in the delivery tracker/PR.
- **P0** = security, privacy, data-loss, or release blocker; **P1** = core product; **P2** = simplification and reliability; **P3** = conditional growth.
- Effort is indicative (S: 1–2 days; M: 3–5 days; L: more than 5 days), not a commitment. Re-estimate after discovery.
- Do not expose secrets in tickets, logs, test fixtures, documentation, or this plan. Credential rotation must happen through the relevant provider consoles and secret manager.

## Reconciled decisions

| Topic | Consolidated decision |
|---|---|
| Primary navigation | Five destinations: **Home, Stories, Notices, Market, Places**. Search and Post are prominent actions, not additional destinations. Lost & Found is a prominent action within Notices and the Post flow—not a sixth top-level destination. |
| Stories | Present one coherent Stories experience; migrate/redirect news, photo stories, and short street submissions without losing their useful format, attribution, or history. Culture/events are simplified and folded into Stories or Notices as appropriate; retain structured event fields only if product evidence requires them. |
| Notices and lost/found | Keep official/community distinctions, verification, expiry, and moderation. Make Lost, Found, and Missing Person obvious; keep their fields and safety rules distinct where needed. Never merge urgent missing-person reporting into an undifferentiated feed. |
| Place and professional listings | Keep Places as the durable local directory. Fold useful business records into place pages and/or Market seller information only after mapping ownership, claims, media, reviews, and redirects. Do not discard records solely because the standalone directory is retired. |
| Admin | Simplify navigation and daily workflows, not essential controls. Retain Dashboard, Moderation, Content, Users/Roles, Settings/Site Content, Taxonomy, Security/IP blocks, Audit, and Backup/Restore. Ads are inquiry-only or feature-flagged until demand is proven. Keep destructive-action safeguards and auditability. |
| Revenue | Defer payment processing, paid boosts, subscriptions, and self-serve ad billing. A static advertiser contact path may remain. Do not accept or orphan live payments during retirement. |
| Communication | Remove full in-app marketplace chat in favor of safe Call/WhatsApp contact actions only after confirming there are no active conversations requiring retention or export. Keep submission receipts and essential transactional notices; defer marketing digests and push notifications. |
| Automation and cron | Establish one canonical production scheduler and deployment owner first. Retain only scheduled jobs with a proven operational purpose (e.g. publish, notification, database maintenance, backup); turn digest/AI/state jobs off only after checking dependencies. The target is a small, monitored set—not a predetermined count. |
| Data model | Reduce unused complexity in reversible batches. Audit counts, foreign keys, RLS, RPCs, storage objects, exports, legal retention, and rollback before proposing any table or column removal. Agree a realistic table-count target after inventory; the audits' ≤35/≤45 targets conflict and are not release criteria. |
| Performance and offline | Optimize to measured low-end/mobile conditions; prioritize a resilient reading experience and resumable local draft/submit behavior. Do not promise background sync where browser support or server idempotency is not verified. |
| Language and accessibility | Preserve complete EN/FR support on retained journeys. Start with short, reviewed Pidgin share/help copy only if community review supports it; do not claim full Pidgin translation or rely on browser speech recognition as the sole input path. |

## Phase 0 — Verify the baseline and control risk (P0, start immediately)

- [ ] **0.1 Assign decision owners and freeze scope.** Name a product owner, technical owner, data/security reviewer, moderator representative, and deployment owner. Approve the five core jobs and record the reconciled decisions above. **Done when:** the team has owners, an agreed first release boundary, and an explicit list of deferred features.
- [ ] **0.2 Establish a known-good baseline.** Record current branch/commit, environment, build/typecheck/lint/test status, deployment targets, current routes, job schedules, database migration state, table/policy inventory, bundle/Lighthouse baselines, and outstanding worktree changes. **Done when:** the baseline is reproducible and unrelated in-progress changes are not mistaken for upgrade changes.
- [ ] **0.3 Validate the reported credential exposure.** Have the security owner inspect the referenced security documentation and provider history without copying key values into the plan. If exposure is confirmed or cannot be ruled out, rotate affected credentials (service-role, encryption, storage, email, payment, and other exposed secrets as applicable), update the secret manager, redeploy, revoke old values, and verify old credentials fail. **Done when:** exposure status and rotation date are documented without values, affected services work with new credentials, and old credentials are revoked. If not confirmed, record evidence and an owner-approved decision.
- [ ] **0.4 Harden anonymous submission before promotion.** Inventory all public write endpoints; verify CAPTCHA/Turnstile policy in staging and production, rate limiting, IP blocks, honeypot coverage, abuse logging, and explicit failure behavior. Avoid silently accepting submissions when required anti-abuse configuration is absent. **Done when:** automated and manual tests show protected requests are challenged or rejected as configured, with no accidental CAPTCHA bypass.
- [ ] **0.5 Audit marketplace PII and file uploads.** Trace listing-contact data from database through views, queries, HTML, server actions, logs, and caches. Verify contact reveal is authenticated/authorized as intended, rate-limited, and logged; check image MIME/size limits and EXIF/GPS handling. **Done when:** no unapproved phone/email/location data is returned in public page source or broad database reads, and upload constraints are tested.
- [ ] **0.6 Create operational recovery points.** Confirm a fresh, restorable database backup and object-storage recovery/versioning before schema or storage changes. Test restore in an isolated environment; record RPO/RTO and the operator/runbook. **Done when:** an independent reviewer can restore the backup without production writes.
- [ ] **0.7 Resolve deployment and scheduler ownership.** Identify the actual production host, deploy path, scheduler, DNS/cron ownership, and rollback mechanism; compare workflows and configuration to what runs in production. Disable duplicate schedules only after proving which one is canonical. **Done when:** one documented source of truth exists and a missed/duplicate job can be detected.
- [ ] **0.8 Confirm the supported framework conventions.** Before implementation, consult the repository's installed Next.js guidance and project architecture checklist for touched routes, cache behavior, locale routing, metadata, and server actions. **Done when:** planned changes respect current repository conventions and gates.

## Phase 1 — Deliver a simple, trustworthy core experience (P1)

- [ ] **1.1 Publish the core information architecture.** Implement the five destinations in navigation on mobile and desktop; expose Search and a clearly labeled Post action separately. Keep the locale resolution and localized link rules intact. **Done when:** 320px/mobile and desktop checks pass, the primary destinations are understandable without relying on icons alone, and locale/bare-href audits pass.
- [ ] **1.2 Make Notices and Lost & Found discoverable.** Add clear Lost, Found, Missing Person, and Community/Official Notice entry points; support place, freshness, status, and expiry as appropriate. Keep official verification visibly distinct from community submissions. **Done when:** a first-time user can find the correct action without first understanding internal content-type names; urgent and sensitive notices retain appropriate moderation/escalation.
- [ ] **1.3 Create one understandable Post entry point.** Replace multiple competing entry points with a guided start that offers clear choices (e.g. Story, Lost/Found, Notice, Sell), then only the fields relevant to that job. Preserve distinct validation and moderation rules; do not auto-classify sensitive notices without user confirmation. **Done when:** guest flows are documented, form fields are job-specific, and a representative first-time user completes each core flow without staff assistance.
- [ ] **1.4 Simplify lost/found submission.** Provide a short mobile-first form for item/person description, place, optional photo, safe contact preference, and relevant timing. Support text as the universal fallback; add voice assistance only as progressive enhancement with permission, localization, and manual correction. **Done when:** EN/FR flows are screen-reader usable, usable without microphone support, and tested on small screens and slow connections.
- [ ] **1.5 Simplify the Market listing and buyer journey.** Keep title/description, optional small number of photos, price/currency where relevant, category, place, and contact. Show clear scam-safety guidance; offer Call/WhatsApp only through the privacy-safe contact mechanism. Require stronger contact verification only if the product owner approves the friction and the abuse case supports it. **Done when:** a seller can post without unnecessary account/editor fields, buyers see safety guidance, and contact details do not leak into public HTML or cached pages.
- [ ] **1.6 Strengthen Places as the cross-content hub.** Make place pages connect relevant stories, notices, and listings; merge professional/business details only where ownership and moderation are clear. Keep static/list-first discovery fast; make maps optional and lazy-loaded. **Done when:** place navigation is useful without map JavaScript, and no existing claim or verified-business record is lost.
- [ ] **1.7 Consolidate the Stories experience safely.** Unify discovery of news, photo stories, and short community stories while preserving format-specific presentation, dates, attribution, corrections, translations, media, and canonical URLs. Fold Culture/Events into Stories/Notices only after content mapping; retain date/place/venue fields if they serve a demonstrated user task. **Done when:** all retained content remains findable, searchable, attributable, and linked from migrated/redirected URLs.
- [ ] **1.8 Preserve editorial trust and user recourse.** Keep pre-publication moderation, reports, corrections register, takedown/privacy requests, contributor credit, verified/official badges, and submission status/history. Add an explanatory badge label and make correction reporting available on every retained content type where correction is meaningful. **Done when:** each public content flow has a documented report/correction route and audit trail.
- [ ] **1.9 Improve empty, loading, and failure states.** Add localized next-step guidance for empty feeds/forms, retryable errors, upload progress, and slow/offline connections. Use cached reading only where content freshness/privacy rules are respected. **Done when:** failures never look like successful submission, and every empty core destination gives a useful next action.
- [ ] **1.10 Maintain accessibility and bilingual parity.** Check touch targets, contrast, text scaling, keyboard navigation, screen-reader labels, visible focus, and EN/FR string parity across Home, Stories, Notices/Lost & Found, Market, Places, Post, and account receipts. **Done when:** the accessibility and locale checks pass and no critical task depends on color, icon, speech, or one language alone.

## Phase 3 — Low-bandwidth, reliability, and safety improvements (P1/P2)

- [ ] **3.1 Measure before optimizing.** Capture representative mobile/slow-network baselines: LCP, INP, CLS, public JS transfer, image bytes, server response, query counts, and key-flow completion. Use current Lighthouse/browser tooling and a documented device/network profile. **Done when:** repeatable before/after evidence exists; do not substitute a guessed bundle target for user outcomes.
- [ ] **3.2 Optimize images and uploads end to end.** Client-resize/compress with a conservative cap and one-photo default where appropriate; retain server-side validation/transformation, byte/MIME checks, upload limits, progress, retry/resume behavior, EXIF stripping, and accessible errors. **Done when:** real mobile uploads succeed on constrained connections and stored/served files satisfy agreed byte and dimension budgets.
- [ ] **3.3 Improve public loading performance.** Prioritize the actual LCP image, lazy-load maps/heavy widgets, remove unused client code, use optimized image components, inspect fonts, reduce duplicate homepage queries only where traces show a bottleneck, and apply framework-supported caching with correct invalidation. **Done when:** core routes meet agreed field/lab performance budgets without stale private or urgent content.
- [ ] **3.4 Add safe offline reading and draft recovery.** Define a service-worker cache allowlist for public, non-sensitive content; handle version changes, cache eviction, locale, and logout. Persist drafts locally with clear status and a retry path. **Done when:** offline reading works for intended pages and drafts survive refresh/reconnect without duplicate posts.
- [ ] **3.5 Add an offline submission outbox only with server idempotency.** Define submission IDs, duplicate protection, consent/privacy for locally stored contact data, deletion/expiry, attachment handling, retry policy, and an explicit queued-versus-received receipt. Background Sync is progressive enhancement, not a requirement. **Done when:** airplane-mode tests prove drafts are neither falsely reported as received nor lost/duplicated on reconnect.
- [ ] **3.6 Improve location and contact choices.** Make manual place selection obvious and GPS optional; explain permission/failure and never require precise coordinates for a usable post. Provide contact preference and avoid exposing precise reporter location or contact data to public caches. **Done when:** indoor/GPS-denied and no-permission journeys pass.
- [ ] **3.7 Reduce search and page-query overhead.** Debounce suggestions, cancel stale requests, scope to core content types, and tune query batching based on profiling. Retain robust search behavior and localization; defer embeddings unless measured relevance warrants operational cost. **Done when:** suggestions are responsive on simulated high latency and request volume is bounded.
- [ ] **3.8 Improve delivery and observability.** Ensure error monitoring is tied to deploy releases, health/readiness checks disclose no secrets, scheduled jobs report outcome, and backup/restore is exercised on a schedule. **Done when:** test alerts reach an owner and a documented incident drill succeeds.

- [ ] **4.1 Build the regression matrix before release.** Include localized routing and redirects; guest Story, Lost, Found, Notice, and Market submissions; moderation/verification; publication; account status; correction/report; contact reveal/privacy; media upload; backup/restore; and failure/slow/offline paths. **Done when:** critical journeys have automated or repeatable manual checks with owners.
- [ ] **4.2 Add the missing end-to-end journeys.** Test a guest lost/found report through receipt and moderation, plus a trader listing through publish and privacy-safe contact; exercise EN/FR and narrow viewport. Add offline/retry coverage where supported. **Done when:** tests catch regressions end-to-end, not only in isolated query helpers.
- [ ] **4.3 Verify database and authorization changes.** Run type generation/checks, migration verification, database lint, RLS harness/integration tests, route/server-action guards, and migration tests against a clean database and a production-like staging copy. **Done when:** no unexpected schema drift or policy regression exists and test reports are attached to release evidence.
- [ ] **4.4 Validate redirects, SEO, and discoverability.** Generate a source-to-destination map for retired routes; preserve meaningful query parameters/content IDs; check localized canonical/hreflang metadata, sitemap, robots, structured data, and redirect chains. **Done when:** internal links are updated, external links land on relevant pages, and sitemap/locale/bare-href checks pass.
- [ ] **4.5 Run a staged release.** Deploy schema-compatible code and reversible feature flags to staging; verify data, jobs, monitoring, and user journeys; then canary production, monitor errors/abuse/performance, and expand gradually. **Done when:** rollback is demonstrated, no critical data or trust issue is open, and release owner approves.
- [ ] **4.6 Close the loop after launch.** Review first-week support reports, moderation load, failed submissions, old-route traffic, mobile performance, spam/scams, and community feedback. Fix regressions before beginning conditional growth work. **Done when:** owner records a launch review and prioritizes evidence-backed follow-up.

## Phase 5 — Conditional growth (P3; do not start until core signals justify it)

- [ ] **5.1 Pilot a champion/community toolkit.** Produce reviewed printable/poster materials and reusable WhatsApp group copy; recruit pilot places and a moderation contact before building referral machinery. **Start when:** named pilot communities agree to participate. **Done when:** pilots produce measurable repeat submissions without unsustainable moderation.
- [ ] **5.2 Add voice-note or speech input as an optional path.** Assess supported devices, language accuracy, consent, storage/retention, transcription review, and accessibility with local users. Preserve typed/text fallback and do not upload audio without explicit consent. **Start when:** field research shows typing is a major completion barrier. **Done when:** tested users can correct recognition errors and opt out.
- [ ] **5.3 Add SMS/USSD intake only after channel and operations validation.** Select provider based on country coverage, cost, sender registration, consent, fraud controls, delivery receipts, and staffed response workflow. **Start when:** feature-phone users are excluded from core journeys and a sustainable operator exists. **Done when:** opt-in, delivery, abuse, support, and data-retention tests pass.
- [ ] **5.4 Revisit digest, push, and WhatsApp Business messaging.** Start with existing share intents and public links. Assess template approval, consent, cost, unsubscribe, privacy, and staffed editorial cadence before automated broadcasts. **Start when:** observed sharing/return behavior supports it. **Done when:** measured value exceeds operational and compliance cost.
- [ ] **5.5 Revisit maps, professional claims, verification, and monetization separately.** Require evidence of user demand, place-data quality, moderation capacity, consumer safety, regulatory/payment readiness, and support ownership for each proposal. **Done when:** each feature has its own approved business case, risk assessment, and staged rollout—not a bundled reactivation.
- [ ] **5.6 Expand language support only with community review capacity.** Keep EN/FR complete; pilot short, reviewed local-language voice/share content before translating the full CMS. **Done when:** named reviewers can maintain accuracy and moderation parity.

## Cross-cutting acceptance criteria

- [ ] **Core usability:** Five primary destinations; Search/Post remain obvious actions; Lost/Found is prominent; core submissions are possible as a guest where safe, in EN/FR, with readable labels and no mandatory microphone/GPS permission.
- [ ] **Trust and safety:** Moderation, official verification, reports, corrections, user privacy, rate limits, audit trail, secure contact reveal, and backup recovery work for all retained features.
- [ ] **Data safety:** No table/object/provider is removed before dependency review, approved retention/export, successful staging migration, regenerated types, RLS/security tests, and a tested recovery route.
- [ ] **Operations:** One documented production deployment/scheduler owner; scheduled jobs are idempotent, monitored, non-duplicated, and have a responsible contact.
- [ ] **Performance:** Core mobile journeys meet agreed measured targets for LCP/interaction/image transfer and work at a documented constrained-network profile. Set numeric budgets from Phase 3 baselines and revise only with evidence.
- [ ] **Quality gates:** Repository check/build, focused unit and end-to-end tests, RLS/security posture, migration/type verification, locale/bare-link/sitemap checks, and accessibility checks pass.
- [ ] **Release safety:** Redirects are intentional, feature flags have owners/expiry, deployment is staged, rollback is proven, and launch issues are monitored.
